## 언제 쓰는가

커밋하기 직전, 특히 동시성(락, 트랜잭션, 비동기 처리)이나 외부 연동(Kafka, Redis, 외부 API)이 얽힌 변경사항에서 엣지 케이스를 놓치지 않았는지 확인할 때.

## 절차

1. **변경 범위 파악**: `git diff`(staged 기준)로 이번 커밋에 포함될 변경 파일과 로직을 파악한다.
2. **리스크 카테고리별 점검**:
   - 동시성: 락 범위, 트랜잭션 경계, 레이스 컨디션 가능성
   - 장애 지점: 외부 API/Kafka/Redis 호출 실패 시 처리(재시도, 폴백, 타임아웃)
   - 엣지 케이스: null/빈 값, 경계값, 동시 요청 시 중복 처리
3. **근거 제시**: 지적한 리스크는 관련 코드 라인을 인용해서 왜 문제인지 설명한다. 추측성 지적은 하지 않는다.
4. **우선순위 정리**: 반드시 고쳐야 하는 것과 알고 넘어가도 되는 것을 구분해서 보고한다.

## 규칙

- 실제 코드에 근거 없는 지적은 하지 않는다 ([[verify]]와 동일 원칙).
- 커밋 대상이 아닌 파일까지 광범위하게 리뷰하지 않는다 — 이번 diff 범위로 한정한다.

## 입력

$ARGUMENTS로 특정 파일/영역을 지정할 수 있다. 비어있으면 staged 변경사항 전체를 대상으로 한다.
